# AARIZO — ISSUE-06 Phase B.2.3: Feature Preservation & Integration Matrix

This matrix catalogs **every existing Child Safety (and directly adjacent Safety Hub) UI feature** across the frontend, classifies its current state honestly against the source code, identifies every feature without a direct B.2.2 backend endpoint, and defines how to preserve UX without compromising security.

**Legend:** `Fully integrated` | `Partially integrated` | `Frontend-only` | `Backend-only` | `Mocked` | `Broken` | `Duplicated` | `Unverified`

## 2. Existing Features With NO Direct B.2.2 Backend Endpoint (Explicit Gaps & Safe Handling)

| Feature Currently in Frontend | Where It Appears | Why No B.2.2 Endpoint Exists | Recommended Safe B.2.3 Handling |
| :--- | :--- | :--- | :--- |
| **Guard Child Re-Entry / Check-In Scan (`RE-ENTRY`)** | `childSafetyService.ts#L504` (`logType: 'EXIT' \| 'RE-ENTRY'`) | B.2.2 `POST /api/children/passes/verify` strictly authorizes exits (`SAFE -> OUT_OF_SOCIETY`). There is no `POST /api/children/:id/check-in` guard endpoint in B.2.2. | Do **not** fake a local check-in. Provide **"Mark Child Returned Safe"** button for `resident`/`secretary`/`admin` via `PATCH /api/children/:id` (`{ status: 'SAFE' }`). Log a follow-up ticket if guard-initiated check-in is desired in a later phase. |
| **Auto-Sync Children from `My Flat` Family Members (`societyService.getFamilyMembers`)** | `childSafetyService.ts#L209-L263` | Family members in `societyService` are legacy local records without relational `ChildProfile` constraints (`flatId`, `residentId`, `exitPermissionMode`). Auto-synthesizing local profiles creates ghost records that fail backend lookups (`404`). | Remove silent local synthesis. Only database-backed `ChildProfile` records from `GET /api/children` are authoritative. Optionally offer a one-click **"Import from Household"** prefill helper in the Register Child modal that still submits via `POST /api/children`. |
| **Guard Quick-Test Demo Pass Buttons** | `ChildGateScannerPage.tsx#L235-L248` | Exposing raw `bearerToken` in `GET /api/children/passes` would allow any guard to forge exits without the caretaker's token. | Remove click-to-scan demo buttons completely. Retain read-only **Active Passes Roster** (`passCode`, child, escort, expiry) for guard situational awareness. |
| **`assignResponder` (`RESPONDING` status + responder name/role)** | `SafetyCommandHub.tsx#L112-L120`, `SecurityEmergencyTerminalPage.tsx#L69-L91` | `ChildSafetyAlert` status machine is `ACTIVE -> ACKNOWLEDGED -> RESOLVED \| FALSE_ALARM` (no `RESPONDING` state or `responderName` column). | For Child Safety Alerts, map guard response strictly to `POST /api/children/alerts/:id/acknowledge` (with optional `notes` capturing dispatched responder details) and `POST /api/children/alerts/:id/resolve` (with `resolutionNotes`). Do not fabricate local `RESPONDING` states for child alerts. |
| **General Non-Child `SafetyCommandHub` Tabs (`ONE_TAP_SOS` non-child, `CONTACTS`)** | `SafetyCommandHub.tsx` | Outside B.2.2 `/api/children` scope (`EmergencyIncident` endpoints exist at `/api/emergency-incidents`, contacts are static emergency numbers `100/101/108`). | Preserve non-child `CONTACTS` and `ONE_TAP_SOS` UI intact while cleanly routing `CHILD_SAFETY` SOS to `POST /api/children/sos` so no non-child UX regresses. |
| **Camera QR Scanner Hardware Integration** | `ChildGateScannerPage.tsx` (currently text input only) | No camera QR library (`html5-qrcode` / Capacitor barcode scanner) is currently installed in `package.json`. | Keep the scanner text/paste input (which natively works with USB/Bluetooth QR scanners and manual token paste) and design a clean `onScan(qrPayload)` callback hook so camera scanning can be plugged in without refactoring API logic. |
